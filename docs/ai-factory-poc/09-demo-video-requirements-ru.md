показанное и озвученное в демо `ai-factory-bootcamp-poc-demo-ru 2.mp4` (08:43).

- Текущий статус, уже реализованный scope и следующий шаг брать из `docs/ai-factory-poc/00-status.md`.
- Этот файл описывает требуемое поведение, но не утверждает, что всё перечисленное уже реализовано.

## 1. Цель PoC

AI Factory должна замкнуть в ReportPortal следующий цикл:

1. Агент генерирует тест-кейсы по требованию.
2. Грейдер оценивает кейсы по 100-балльной рубрике.
3. Кейсы загружаются в Test Case Library как `Draft`.
4. Человек ревьюит кейсы в Library и при необходимости отправляет точечные комментарии агенту.
5. Кейс получает статус `Ready` вручную или через Auto-Ready.
6. Ready-кейс отправляется в автоматизацию.
7. Агент создаёт и прогоняет Playwright-тест; результат Launch связывается с итерацией и кейсом.

ReportPortal должен показывать каждую итерацию, качество результата, стоимость и историю изменений.
PoC относится к первой фазе DF Bootcamp 2026 и должен быть скрыт за feature flag.

## 2. Основные сущности и состояния

| Сущность | Требование |
|---|---|
| Pipeline | В PoC два вида: `Test case generation` и `Test automation`. |
| Iteration | Один запуск pipeline. Новая итерация не изменяет предыдущую и пишет кейсы в отдельную папку `iteration-N`. |
| Generation stages | `Create` → `Grade` → `Upload` → `Review`. |
| Automation stages | `Prepare` → `Develop` → `Review` → `Fix`; `Fix` пропускается, если ревью чистое. |
| Case lifecycle | Только `Draft` и `Ready`. Новые кейсы, включая ручные, начинают с `Draft`. |
| Evaluation | `Evaluated` или `Obsolete`; оценка информационная и сама по себе ничего не блокирует. |
| Review comment | Может быть неотправленным, отправленным/в работе, `Addressed` или `Not addressed`. |
| Fix round | Один точечный раунд исправления одного существующего кейса агентом с последующей переоценкой. |

### Переходы состояния кейса

| Событие | Результат |
|---|---|
| Upload сгенерированного кейса | Создать кейс в Library как `Draft`, добавить AI-маркер, evaluation и долю стоимости. |
| Ручное создание кейса | Создать как `Draft`, без AI-маркера; действие готовности называется `Mark as ready`. |
| `Approve` AI-кейса / `Mark as ready` ручного кейса | `Draft` → `Ready`, записать событие в историю. |
| Auto-Ready при выполнении всех условий | `Draft` → `Ready`. |
| Изменение сценария Ready-кейса | `Ready` → `Draft`, evaluation → `Obsolete`. |
| Успешное исправление агентом | Обновить тот же кейс, затем переоценить; Auto-Ready может снова сделать его `Ready`. |
| Изменение только порога Auto-Ready | Не понижать существующие Ready-кейсы и не применять старую оценку. |

## 3. Pipelines и итерации

### 3.1 Список Pipelines

На странице должны быть видны оба pipeline и их итерации. Для каждой итерации показывать:

- статус итерации;
- требование или набор Test Case ID;
- стадии и их фактические статусы, полученные от pipeline;
- suite score;
- стоимость;
- служебные атрибуты и время выполнения.

Статус внешней стадии не нужно переинтерпретировать. Например, `Queued — waiting for runner`
отображается как получен от pipeline и не становится ошибкой ReportPortal.

### 3.2 Детали generation iteration

В шапке показывать требование, модель, окружение, ссылку на CI и KPI: количество кейсов, оценку,
число Ready-кейсов и стоимость. Ниже показывать четыре стадии:

- `Create`: созданные кейсы как дочерние шаги со ссылками в Library;
- `Grade`: оценки всех кейсов и расшифровку снятых баллов;
- `Upload`: результат записи кейсов в Library;
- `Review`: текущую готовность, reviewer, время, неотправленные комментарии и fix rounds.

Рубрика Grade содержит шесть критериев:

| Критерий | Максимум |
|---|---:|
| Atomicity | 15 |
| Clear steps | 20 |
| Clear expected results | 20 |
| No invented logic | 20 |
| No invented UI | 15 |
| Coherence | 10 |
| **Итого** | **100** |

Для потерянных баллов показывать причины. Не использовать `PASS`/`FAIL` для оценки. Низкая оценка не
блокирует Upload, ручное решение или дальнейший поток.

### 3.3 Retry, Re-run и Compare

- `Retry` повторяет только упавшую стадию внутри той же итерации.
- Успешный Retry продолжает ту же итерацию и сохраняет её папку.
- `Re-run` заново запускает генерацию по тому же требованию и может использовать другую модель.
- Re-run создаёт новую итерацию и новую папку; исходная итерация не меняется.
- Compare сопоставляет стадии, suite score, средние оценки по критериям, результат Auto-Ready,
  число fix rounds, стоимость и длительность.
- В сравнении зелёное означает улучшение, красное — ухудшение с учётом направления метрики
  (для score больше лучше, для стоимости и времени меньше лучше).

## 4. Auto-Ready

Auto-Ready настраивается на уровне generation pipeline:

- настройка включает переключатель и целочисленный порог; демонстрационное значение по умолчанию — `90`;
- проверка выполняется после Upload и после каждого успешного fix round с новой оценкой;
- использовать только актуальную evaluation в состоянии `Evaluated`;
- не выполнять переход при наличии неотправленных review comments;
- Auto-Ready только повышает `Draft` до `Ready` и никогда не возвращает Ready-кейс в Draft;
- изменение сценария делает старую оценку `Obsolete`, поэтому она не подходит для Auto-Ready.

## 5. Подключение к CI

Pipeline появляется в ReportPortal после первого отчёта фабрики. Organization Manager или
Administrator должен иметь возможность связать его с GitLab и задать:

- repository;
- branch;
- trigger token;
- job names;
- models;
- environments.

Токен после сохранения не отображается. `Test connection` проверяет подключение. Если токен удалён,
pipeline получает состояние `Not connected to CI`, а действия, запускающие CI jobs, становятся
недоступны.

## 6. Test Case Library

Существующий экран Library расширяется следующими элементами:

- колонка `Status` со значением Draft или Ready;
- AI-чип рядом с ID сгенерированного или изменённого агентом кейса;
- колонка `AI quality`: score, примерная стоимость и ссылка на source iteration;
- быстрые фильтры `Status` и `AI`;
- пресет `Review queue`, эквивалентный `Draft + AI`;
- боковая панель со статусом, evaluation и основной кнопкой `Approve` для Draft AI-кейса;
- переход `Open Details` на существующую страницу деталей TMS.

AI Factory должна поддерживать оба шаблона TMS:

- `Steps`: precondition и отдельные строки шагов;
- `Text`: precondition и единый блок instructions/expected result.

У ручного кейса нет AI-маркера, но действует тот же lifecycle Draft/Ready.

## 7. Evaluation и стоимость на странице кейса

Показывать:

- итоговый score из 100;
- шесть критериев, их баллы и причины снижения;
- состояние `Evaluated` или серое `Obsolete` с объяснением;
- источник оценки: iteration или fix round;
- приблизительную стоимость генерации кейса;
- token usage по типам и модель;
- ссылки на source iteration и fix rounds.

Стоимость приходит от pipeline, носит информационный характер и не блокирует действия. Стоимость
кейса состоит из его доли generation iteration и стоимости собственных fix rounds.

## 8. Review comments и Push to agent

Reviewer комментирует конкретные части сценария, аналогично строкам merge request:

- в `Steps` — precondition и конкретный шаг;
- в `Text` — precondition и блок instructions/expected result.

Правила:

- неотправленные комментарии блокируют `Approve` и Auto-Ready;
- reviewer может отправить набор комментариев через `Push to agent` или сбросить его;
- Push запускает отдельную CI job исправления;
- агент читает текущую версию кейса из Library и меняет только этот кейс;
- fix round не создаёт новые кейсы и не делит существующий кейс;
- после исправления грейдер заново оценивает кейс;
- показывать diff `before/after`, score до/после и стоимость раунда;
- по каждому комментарию показывать `Addressed` или `Not addressed` и причину;
- успешная новая оценка может запустить Auto-Ready.

Если fix job завершилась ошибкой или timeout:

- сценарий кейса не изменяется;
- комментарии снова становятся неотправленными;
- неудачный fix round остаётся видимым в стадии Review;
- пользователь может повторить Push или сбросить комментарии.

## 9. Ready-only ограничения

- `Add to Launch`, `Add to Test Plan` и `Automate` доступны только для Ready-кейсов.
- Ограничение обязательно проверяется API, а не только UI.
- При bulk-действии над смешанной выборкой обработать только Ready-кейсы, а Draft-кейсы пропустить
  и перечислить в сообщении.
- Если Ready-кейс уже находится в Test Plan и его сценарий изменён, он остаётся в плане, но сам кейс
  становится Draft, evaluation — Obsolete, а запуск плана блокируется.
- На таком кейсе показать `In plan, Launch blocked`.
- В Edit Scenario предупредить о возврате в Draft и предложить `Approve along with these changes`.
- При подтверждении Ready с Obsolete evaluation запросить дополнительное подтверждение.

## 10. Test automation

Ready-кейс можно отправить из Library через действие `Automate`:

1. Диалог показывает выбранные кейсы и environment из CI connection.
2. `Send` создаёт automation iteration со стадиями Prepare, Develop, Review и Fix.
3. Агент получает кейс из Library, а не из Jira, пишет Playwright-тест, запускает и ревьюит его.
4. Если review не нашёл замечаний, Fix получает статус `Skipped`.
5. Финальный зелёный прогон отправляется в ReportPortal как Launch и связывается с iteration и case.
6. Merge request остаётся местом code review в GitLab; ReportPortal только показывает его состояние.

На кейсе показывать automation status и состояние MR. `Last result` берётся из последнего Launch
любого происхождения, а не обязательно из запуска AI Factory; результат может содержать defect type,
например `Product bug`.

## 11. Роли и права

| Роль | Возможности в PoC |
|---|---|
| Viewer | Только просмотр данных AI Factory. |
| Editor | Review comments, Push to agent, Approve, Automate. |
| Organization Manager / Administrator | Всё выше, а также Pipeline settings, CI connection, Re-run и Retry. |

Права должны проверяться API. Скрытие или блокировка кнопки в UI недостаточны.

## 12. Нефункциональные и совместимые требования

- Feature flag обязателен; по умолчанию функциональность выключена.
- При выключенном флаге проекты, не использующие AI Factory, работают как раньше.
- Trigger token не возвращается и не отображается после сохранения.
- Авторизация проверяется на API для всех изменяющих действий.
- Нужны контролируемые timeout/retry для CI jobs и отображение ошибок без потери данных.
- Все значимые lifecycle- и actor-события должны оставаться в аудите/истории.
- Нужна определённая политика хранения iterations, evaluations, costs, comments и diffs.
- Расширения должны быть совместимы с существующим Test Case Library, Test Plans и Launches.
- Данные pipeline считаются источником истины для stage status, token usage и стоимости.

Видео подтверждает наличие этих категорий NFR, но не задаёт конкретные значения timeout, retry count
или retention period. Их нельзя придумывать без канонических требований или решения владельца.

## 13. Критические отрицательные правила

- Не ждать merge request перед Upload кейсов в Library.
- Не использовать Grade как блокирующий quality gate.
- Не показывать PASS/FAIL для grader evaluation.
- Не использовать Obsolete evaluation для Auto-Ready.
- Не понижать Ready-кейс из-за изменения порога Auto-Ready.
- Не перезаписывать кейсы предыдущей итерации при Re-run.
- Не создавать и не делить кейсы во время fix round.
- Не разрешать Draft-кейсу попасть в Launch, Test Plan или automation даже через API.
- Не брать source case для automation из Jira — источник находится в Library.
- Не считать последний AI Factory Launch единственным источником `Last result`.

## 14. Минимальные демонстрационные acceptance scenarios

1. Generation iteration создаёт четыре Draft-кейса, два с score ≥ 90 становятся Ready через Auto-Ready.
2. Кейс с неотправленными комментариями нельзя Approve; успешный Push меняет score `81 → 92`,
   помечает поддержанный комментарий как Addressed и переводит кейс в Ready через Auto-Ready.
3. Просьба разделить кейс возвращается как Not addressed с объяснением ограничения fix round.
4. Timeout fix job не меняет кейс, возвращает комментарии в неотправленное состояние и допускает Retry.
5. Score `88` при threshold `90` оставляет кейс Draft, после чего reviewer может Approve вручную.
6. Ручной кейс без AI-маркера создаётся Draft и использует действие `Mark as ready`.
7. Редактирование сценария Ready-кейса в плане возвращает его в Draft, делает evaluation Obsolete
   и блокирует Launch, пока кейс снова не одобрен.
8. Bulk Add to Test Plan над Ready + Draft добавляет только Ready и называет пропущенный Draft.
9. Automation iteration создаёт Playwright-тест, Launch и связи с iteration/case; чистый Review
   пропускает Fix.
10. Retry восстанавливает упавший Upload в той же iteration; Re-run создаёт отдельную iteration,
    после чего обе можно сравнить.
